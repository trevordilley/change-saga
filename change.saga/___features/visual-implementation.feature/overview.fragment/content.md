# Explain mechanisms with an authored technical account {#explain-mechanisms-with-an-authored-technical-account}

A feature implementation deck combines a detailed overview with ordered visual slides. The overview explains responsibilities, models, execution paths and tradeoffs; slides make those mechanisms easier to inspect. A short Front summarizes each slide, while its Back carries the detailed diagram.

Semantic Items connect visual elements to exact source evidence and, where appropriate, product intent. Diagrams can express flows, relationships, sequences, boundaries and surprises. A diagram should make a relationship visible rather than turn a list of filenames into boxes.

Application-wide design lives in the [approach essay and four whiteboards](/technical). Feature decks explain focused mechanisms, and review decks explain changes between commits.

## Keep the visual explanation connected to evidence

A whiteboard element can pin exact code, link to a saved criterion or technical definition, select an explicit inventory code subset and open a related record. Readers use the same separate evidence actions and slide-out drawer as slide Items. The [accepted whiteboard evidence story](/requirements/whiteboard-element-evidence) states the product obligations.

Code changes make the affected element stale in the reader and in the shared reference, health and reconciliation reports. An author must reassess its meaning and publish a new complete revision with the observed parent; historical revisions retain their original pins. Only current active board evidence and eligible selections contribute living documented-code coverage.

Positive, negative and edge verification definitions link these criteria to the CLI lifecycle, server rejection and clicked browser tests. The Architecture board itself links its Whiteboards element and ownership boundary to these criteria and exact implementation code.
